# K-Ship Guard AX — 평가 결과

정의서 1장의 측정 지표 4개를 합성 시나리오 40건으로 잰 결과입니다.

- 시나리오: [`data/eval/scenarios.jsonl`](../data/eval/scenarios.jsonl) — 개발용(dev) 30건 D01~D30, 확인용(holdout) 10건 H01~H10
- 정답 작성 방법과 판단 관례: [`data/eval/README.md`](../data/eval/README.md) (구현 코드를 보지 않고 rules.yaml·법령·별표만 보고 작성)
- 실행: `.venv/Scripts/python -I scripts/evaluate.py --split dev|holdout`
- 사례별 결과: `data/eval/results_dev.json`, `data/eval/results_holdout.json`

판단 경로(문장 추출 → 기술 후보 → 규칙 엔진 → 근거 연결)만 평가합니다. LLM 설명 문장과 의미 검색은 권고·근거에 영향을 주지 않으므로 끄고 돌립니다.

틀린 2건은 모두 **더 엄격한 쪽**으로 틀렸습니다. 정답보다 느슨한 권고(위험한 자료를 '진행 가능'으로 낸 경우)는 dev·holdout 모두 0건입니다.

### 읽는 법

- 근거 ID 정밀도가 0.5 안팎인 것은 의도된 동작입니다. 시스템은 규칙마다 판례 카드를 여러 장 붙이는데, 정답은 핵심 근거만 적습니다. 판단에 쓴 근거가 빠지지 않는 것(재현율)을 우선했습니다.
- 질문 재현율 1.0은 "물어야 할 것은 다 물었다"는 뜻입니다. holdout의 정확 일치 0.5는 문장에 이미 있는 정보를 놓쳐 다시 물은 경우입니다 (아래 표).

## holdout 오류 분석 (튜닝하지 않음)

holdout은 dev 조정을 마친 뒤 **한 번만** 돌렸고, 결과를 보고 코드를 고치지 않았습니다.

| 사례 | 무엇이 틀렸나 | 원인 | 방향 |
|---|---|---|---|
| H01 | 진행 가능 → 조건부 진행 | 영어 문장 "Korean supplier"(국가), "not from any government-funded R&D"(국가 R&D 아님)를 못 읽음 → 되물음 → P1로 조건부 | 문장 추출 한계 (안전한 쪽) |
| H02 | 진행 가능 → 법무팀 검토 필요 | 별표 S04의 수치 조건(직경 5m 이상 프로펠러)을 보지 않고 '프로펠러'만으로 후보를 올림 | 별표 수치 조건 확인 필요 (안전한 쪽) |
| H05 | 불필요한 질문 2개 | "국책 X" 표기를 못 읽음. 기술 후보 미확정 시 어느 기술인지 되묻는 것은 정답 관례와 다름 (dev D13과 같은 관례 차이) | 문장 추출 한계 / 관례 차이 |
| H06 | 기술 S08 추가 | 방벽·화물창 자료에서 S08도 함께 후보로 올림 (dev D02~D04와 같은 관례 차이) | 관례 차이 |
| H07 | 불필요한 질문 1개 | "승인도면 리스트**엔** 없는"(에+는 축약)을 못 읽음 | 문장 추출 한계 |
| H09 | 불필요한 질문 1개 | "러시아 조선소"를 수신자 유형으로 못 읽음 | 문장 추출 한계 |
| H04 | 근거 1개 누락 | 국내 이전인 국가 R&D 산출물에 국가연구개발혁신법 제21조를 연결하지 않음 (규칙표에 없는 정답 작성자 판단) | 규칙 추가 검토 |
| H08 | 근거 1개 누락 | 하도급법 판례 PREC-2018누77120이 카드 수 제한으로 빠짐 | 카드 우선순위 조정 |

## dev에서 고친 것

dev 오답을 보고 고친 것은 모두 **일반 규칙**이고, 특정 문장에 맞춘 예외는 넣지 않았습니다.

- 문장 추출(`request_parse.py`): 부정 표현("NDA 안 썼어요", "국책과제 아님"), 해외법인·외주사·업체 같은 수신자 표현, 라이선서명 → 국가, 영어 문장, 번역기(파파고·DeepL 등)를 외부 AI로 보기, 승인도면 목록 포함 여부("목록 포함", "목록에 없음")
- P1 적용 누락 수정(`rules_engine.py`): rules.yaml의 P1은 "기술 후보가 없을 때만 진행 가능"인데, 엔진은 필수 항목만 확인하고 있었음. 기술 후보가 있고 걸리는 규칙이 없으면 '조건부 진행 — 사내 반출 승인(관리책임자) 받기', 근거 지침 제13조 제4호
- 기술 ① 지표: 사원이 직접 고른 카테고리는 빼고 시스템이 자료에서 찾은 후보만 셈 (판단에는 둘의 합집합을 그대로 씀)

## dev에 남은 차이 (정답 관례와 시스템 정책이 다름)

| 사례 | 차이 | 시스템을 바꾸지 않은 이유 |
|---|---|---|
| D02·D03·D04 | 화물창 단열·방벽 자료에서 S08을 함께 후보로 올림 | 기술 후보는 위험을 올리는 쪽(합집합)으로 잡는 것이 정의서 원칙 |
| D13 | '탱크'만 보이는 자료에서 어느 기술인지 되물음 | 기술 후보 미확정(P2)일 때 사원에게 확인을 받는 것이 화면 흐름의 일부 |

## 한계와 공정성 메모

- 시나리오는 합성입니다. 실제 사내 요청 문장의 분포와 다를 수 있습니다.
- holdout H05에는 '펌프'라는 약한 단서가 나옵니다. 약한 단서 처리(`terms.weak_candidates`)는 dev D13의 '탱크' 사례를 보고 만든 일반 규칙이지만, 정답 작성 보고서에서 H05에 '펌프'가 있다는 것을 미리 본 상태였습니다. 이 점을 밝혀 둡니다.
- 규칙 ID 참고 지표(정밀도 0.94/0.87, 재현율 0.73/0.81)에서 놓친 것은 R07·R09 '질문만 하는 경우'(계약 근거·수신 국가 미입력)입니다. 시스템은 이것을 규칙 적중이 아니라 질문(④)으로 내보내므로 셈 방식 차이입니다.
- 도면 YOLO는 정답 작성에 쓰인 P&ID 샘플만 돌렸습니다. 도면 분석 자체의 정확도는 따로 쟀습니다: 검증 mAP50 0.33 (`models/yolo/pid_groups_metrics.json`).
